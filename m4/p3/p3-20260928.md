# m4/p3: learned expert eviction for the tiered-experts cache, 2026-09-28

**Decision: NO-GO.** Across every model, capacity, fold and upload-cost model, the learned policy (logistic or a
16-unit MLP) ends up within -1.6% to +1.5% of the best simple policy (a)-(d) in simulated ms/token. The bar was
+3%. Phase 2 was not started. There was no build, no GPU window and no downtime, and no mistral.rs code changed.
Worktree `mr-p3` (branch `p3-learned-evict`, at ktrace 8cff156) exists but has no changes.

Everything here is CPU-only: `sim.py` under `run.sh` (systemd-run MemoryMax=4G), about 6 min per 35B config and
9 min per 80B config.

## Traces and held-out protocol

| model | train | held-out | capacity |
|---|---|---|---|
| 80B Qwen3-Next Q4_K_M (48 layers, 512 experts, top-10) | `m4/next/out/next-calib.trace` (m3 calib prompts, 3802 decode tokens) | `next-eval-base.trace` (m4 prompts-eval, 40 x 64, 2522 tokens) | 143 slots/layer (0.28, the recommended config) |
| 35B Qwen3.6-35B-A3B UD-Q4_K_XL (36 traced layers, 256 experts, top-8) | half the prompts of `m4/out/q35-calib.trace` | the other half (2 folds: even/odd prompts, then swapped); about 5100 tokens each | 169 (0.66, the gated runs) and 159 (0.62) |

- **No 35B held-out trace exists.** `q35-calib.trace` is the only per-token 35B trace, so the 35B uses a
  prompt-disjoint 2-fold split, and the profile for (a) is built from the train half only. Collecting a new trace
  would have needed a GPU window, and at NO-GO it was not worth one.
- **80B check.** The static profile from `profile-next.txt` gives 81.5% (143 slots) and 82.4% (148 slots) offline.
  These exactly match the measured W2/W1 hit rates.
- **Tuning.** Every tunable (the LFU decay/margin, the admission k/window, the learned horizon N and score margin)
  is chosen on the train prompts only, using cross-fitting: the profile comes from one half and the tuning data
  from the other. Without this, the in-sample profile makes every adaptive policy look worse than static.
- **Learned model.** Trained on train-prompt traces only, with its placement prior out of sample. Held-out
  prompts were never used for fitting or tuning.
- **P1 feature missing.** P1's lookahead prediction is not in the traces (`TITAN_TIERED_TRACE` logs gate ids only),
  so the model does not use it.
- **Learned features.** Per (layer, expert): profile prior, decayed use counts (decay 0.5/0.8/0.95), recency,
  request prefill fingerprint, used-this-token, layer, and prior x used.
  - Target: routed again within N tokens (N in {4, 16, 64}).
  - The score drives both eviction (evict the lowest-scoring resident not used this token) and admission (a miss
    is admitted if its score beats the victim's by a tuned margin).

## Cost model (ms/token = base + misses x c_miss + uploads x c_up)

`base` is fitted so that static placement reproduces the measured tok/s. On the 80B that is 28.5 tok/s
(recommended config, W2): base 25.2 ms. On the 35B it is 78.0 tok/s (owned, W2): base 10.6 ms. The 35B misses
are scaled by 40/36 for the 4 layers that were not traced.

| model | c_miss per missed expert (gate+up+down) | c_up per promoted expert |
|---|---|---|
| 80B | 111 us = 3 x 37 us/task (final config, p1-20260928.md). Cross-check: W2 lowest-id to profile gives 130 us. `nvme` column: 3 x 86 us (W1) | **390 us**, derived from W2's P2 fingerprint run: 12512 uploads cost 3.7 s net of its +0.8% hit rate, about 5 GB/s effective for 2.0 MB |
| 35B | 75 us = 3 x 25 us/task | 380 us (the same 5 GB/s for 1.9 MB) |

Other cost columns:
- `fastup`: c_up = 80 us, about 25 GB/s. The link is PCIe 5.0 x16 at 32 GT/s (sysfs).
- `async`: c_up = 0, meaning the copy is fully hidden but the expert is usable only from the next token.

Today's uploads (`touch_and_admit`, `reseed`) are synchronous pageable `memcpy_htod` calls on the decode thread,
so `sync` is the current reality. The hit cost is taken as 0 because the GPU gemv is one launch per projection
whatever the hit count.

## Go / no-go

Best learned policy compared with the best of (a)-(d), in simulated ms/token on held-out data, under the cost
model each policy was tuned for:

| case | best (a)-(d) | best (e) | learned gain |
|---|---|---|---|
| 80B 0.28, sync | static 35.09 | MLP 35.64 | **-1.6%** |
| 80B 0.28, async | LFU 31.98 | logreg 31.50 | **+1.5%** |
| 35B 0.66 A / B, sync | LFU 11.83 / admit 12.11 | MLP 11.95 / 12.15 | **-1.0% / -0.3%** |
| 35B 0.66 A / B, async | LFU 11.22 / 11.64 | MLP 11.18 / 11.62 | **+0.3% / +0.2%** |
| 35B 0.62 A / B, sync | LFU 11.71 / 12.03 | MLP 11.86 / 12.05 | **-1.2% / -0.2%** |

None reaches +3%, so the decision is NO-GO. The learned score's features are the same as LFU's (a decayed count) plus
a prior and recency. Once the admission margin is tuned, it makes nearly the same decisions as LFU with a margin.
The prefill fingerprint and layer features add nothing that survives held-out evaluation. This matches P2's
negative result.

## What the simulation does say (for later, not shipped)

1. **80B with synchronous uploads: nothing beats static.** Even the hindsight-optimal static placement is only
   3.2% better (33.97 ms). A promoted expert costs about 3.5 CPU misses (390 us vs 111 us), and at 28% capacity the
   extra hits do not repay that.
   - Promotion helps only if uploads leave the critical path. Async LRU/LFU/learned reaches 31.5-32.0 ms, 9-10%
     under static.
   - That needs about 56-61 uploads/token x 2 MB, roughly 3.3 GB/s sustained at 28 tok/s, from pinned staging on a
     second stream. It also needs a slot-map swap that is safe against in-flight kernels.
   - The source bytes come through the mmap, so NVMe reads add to that load. The `async` column is an optimistic
     bound.
2. **35B: plain LFU-with-margin promotion looks like a real 5-9% win in simulation, even with sync uploads.** It
   costs only about 0.3 uploads/token: an expert is admitted when its decayed count (0.98/token) beats the weakest
   resident's by 4-6. Caveats before building it:
   - (i) The simulated static here uses a 20-prompt profile. Production uses the 40-prompt `profile-q35.txt`
     (93.3% measured), so the headroom is smaller. Fold B at 92.9% static still shows 5.5%.
   - (ii) Any non-static policy in owned mode keeps every expert on the host (`build()`), which adds about 12 GB.
     The 16G service cannot hold that, so it would have to use `TITAN_TIERED_MMAP=1` (77.1 vs 78.0 tok/s owned).
   - (iii) The 35B upload cost is derived from the 80B P2 measurement, not measured on the 35B.

   An LFU-margin policy (a few lines in `touch_and_admit`) plus one GPU window to measure it is the cheap follow-up.
   It is not a learned model.
3. **LRU as implemented (admit every miss) is the worst option** on both models under sync uploads: +60% on the 80B
   and +12-19% on the 35B.

## Files

- `sim.py`: the simulator. It covers the policies (a)-(f), the cross-fit tuner, the learned-model training
  (sklearn), and the cost model.
- `run.sh CONFIG.json`: runs one config under MemoryMax=4G.
- `next80*.json`, `q35-*.json`: the configs, including the cost parameters.
- `out/*.log`: the tables above. `out/*.json` holds the raw counts. `out/*.logreg.npz` holds the fitted logistic
  weights (mu, sd, w, b, N, margin).
