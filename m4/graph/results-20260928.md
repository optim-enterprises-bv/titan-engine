## Step 1: where the decode time goes

nsys (window 1, `out/nsys-*.nsys-rep`, `gaps.py`, `budget.py`) under-reports nothing about kernels but inflates
host launch cost (~2 us per API call: median traced step 17.9 ms vs 11.6-12.2 ms untraced, MTP off), so the bound
comes from untraced runs with the CPU misses switched off (`TITAN_TIERED_DEBUG_SKIP_MISSES=1`, window 2):

| per decode step (median) | MTP off | MTP=2 (2.70 tok/step) |
|---|---|---|
| GPU ops per step (trunk / routed-expert region) | 2113 / 610 | 3584 / 885 |
| kernel busy (nsys) | 7.1 ms | 14.5 ms |
| untraced step, normal | 11.6 ms (86.4 tok/s) | 24.0 ms (112.3 tok/s) |
| untraced step, CPU misses skipped | 9.1 ms (109.8 tok/s) | 19.6 ms (137.9 tok/s) |
| => CPU misses + their syncs (graphs cannot touch) | ~2.5 ms | ~4.4 ms |
| => all non-kernel time without CPU misses (launch, gaps, syncs) | ~2.0 ms | ~5.1 ms |
| upper bound for graphs (~80% of that is in trunk segments) | ~1.6 ms = ~13% | ~4.1 ms = ~17% |

Above the 5% bar, so implemented. (The m-* runs with TITAN_TIERED_TIMING=1 are much slower, 76 / 55 tok/s: that knob
reads /proc per miss pass; don't benchmark with it.)

## Design

`mistralrs-core/src/models/titan_graph.rs` (SegmentGraphs) + `forward_trunk_graphed` / `forward_verify_graphed`
in `quantized_qwen35_moe.rs`. Piecewise, one graph per segment between host syncs:
GDN layer = [previous layer's routed combine + shared expert + residual, attn_norm, GDN (gather, conv, recurrence,
scatter into the pool), residual, post norm, router, top-k]; full-attention layer = [.. up to q/k/v/gate] + eager
KV append and attention + [gate, wo, residual, norm, router, top-k]; plus a final [combine, norm]. Routed experts
(ids sync, CPU misses, uploads), embedding, lm head, MTP draft head stay eager. MTP verification (n rows) uses the
same cut, keyed by n; its GDN rollback snapshots are segment outputs. 51 graphs for decode, 51 for verify n=3.
- 1st call of a segment: eager, warming candle's capture HtoD cache (dims/strides uploads). 2nd: captured
  (RELAXED, event tracking off, stream-ordered allocs become graph memory nodes), then replayed.
- Inputs: another graph's output buffer is read in place; anything else (embedding, positions, state indices,
  routed experts output, attention output) is copied into a segment buffer before launch (~1.8 copies/segment).
- Outputs are copied at the end of the graph into buffers allocated outside graph memory, so every graph
  allocation is freed inside its graph and graphs share physical memory: 32 MiB graph memory for all 102 graphs
  (was 1632 MiB for 51 when graphs owned their outputs, and later captures OOMed).
- Per-step values: positions and state indices are inputs; KV write offset and attention length stay eager;
  recurrent slot and state-pool addresses are in the key (pool reset is now in place, so no re-capture per request).
- Fallback: a segment whose capture/instantiate/upload fails stays eager (logged). Prefill, batch > 1, paged attention,
  device mapping and TITAN_TIERED_LOOKAHEAD > 0 run eager (so the 80B P1 config gets no graphs yet).
- Tiered auto plan reserves TITAN_CUDA_GRAPHS_RESERVE_MIB (default 256) extra when graphs are on.

| (b) tok/s MTP off, 40 x 256 | 82.0 -> **84.4 (+2.9%)** |
| (b) tok/s MTP=2, 40 x 256 | 97.9 -> **100.4 (+2.6%)** |
| (b) 80B | not run (its config uses LOOKAHEAD=2, which graphs skip) |
| (c) ~13k prompt, service config, graphs on | **FAILED**: 1st request ok (13017 tokens), 2nd identical request -> CUDA_ERROR_ILLEGAL_ADDRESS at its first decode steps after the prefill |
| (d) nvcc-free build | links (`build-oxide3b.log`, no nvcc) |

(c) likely cause: `fast_mmvq`'s shared q8_1 workspace (mistralrs-quant and candle) is grow-on-demand and *freed*
on growth; every captured GEMV bakes its address. A bigger request after capture (long-prompt/MTP catch-up path)
frees it and the graphs read freed memory; the short-prompt gates passed because the freed block still held the
right bytes. da11fc3 + candle 19c31e5 never free a grown-out workspace. Untested (no window left), and no
graphs-off control of two back-to-back 13k prompts was run, so a pre-existing failure is not excluded.
