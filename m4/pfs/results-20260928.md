## Design

- **Switch.** `TITAN_PFS=1`. A tiered MoE layer whose chunk has at least `TITAN_PFS_MIN_ROWS` (128) tokens computes
  every routed expert on the GPU. Shorter passes (decode, MTP verify, short prompts) take the old path unchanged.
- **Fixed-order stream** (`mistralrs-quant/src/gguf/titan_pfs.rs`). Every tensor's non-resident experts
  (layer 0..L, gate/up/down, expert id ascending) stream in one fixed sequence through a ring of device staging
  buffers, one projection's non-resident experts per buffer, on a copy stream owned by a worker thread.
  - Copy for item k+R waits on the `used` event of item k (recorded on the compute stream after its kernels).
  - The compute stream waits on item k's copy event.
  - The host keeps R items issued ahead, so the next layers' copies run while this layer computes.
  - Out-of-order use (a new pass) resyncs the sequence.
  - The ring lives only during a prompt. The next non-streamed tiered forward (the first decode step) frees it,
    so decode sees exactly the static placement. No slots are borrowed and the placement never changes.
- **Host memory.** The owned host store (service) is page-locked in place with cuMemHostRegister, and the copy
  engine runs at 42-45 GB/s. Mapped stores (80B, `TITAN_TIERED_MMAP=1`) go through 8 x 16 MiB pinned bounce
  buffers filled by 4 helper threads. `TITAN_PFS_SHARE=f` streams only the hottest share; the CPU twin serves the rest.
- **VRAM.** The ring is sized at the first streamed layer from free memory (free plus the pool's unused
  reservation) above the headroom. It is capped by `TITAN_PFS_RING_MIB` (400).
  - Headroom = 1024 MiB + 32 KiB per (token, expert) task + 10 KiB per KV token of the prompt.
  - 13k gets 3 buffers of 90 MiB; 28k gets 1.
  - Without room, the prompt stays on the CPU twin (no OOM).
- **Kernels** (`titan_tiered_pfs.rs`, a child module, so titan_tiered.rs changes only by a field, the
  registration, an idle hook and a small refactor):
  - **MMQ (default).** llama.cpp's grouped `mmq_gguf_{q4_k,q5_k,q6_k}_moe` (cuda-oxide port, already in
    titan-oxide-ffi; no new kernel). A host counting sort dispatches over the resident slots and the staging
    buffer, the input is quantized once (q8_1_mmq), then one launch per buffer (`fast_mmq::grouped_parts`).
  - **GEMV (`TITAN_PFS_KERNEL=gemv`).** The existing slot-map GEMV runs twice, over the slots and over the
    staging buffer. The tasks run in expert-major order, so each expert is read from L2 by all its tokens.
    Bit-identical to the CPU-twin path by construction.
- **Big chunks** (`TITAN_PREFILL_BIG_CHUNK`). The bulk of the prompt runs in larger chunks, and the last stretch
  stays on the 512 grid. So every boundary, and the L resume point, stays on the 512 grid, and turn-2 recompute
  stays under 1 chunk.

## Deploy

- Add `Environment=TITAN_PFS=1` to the service unit; the binary is target-pfs-oxide/release/mistralrs at fbe660747.
- Caveats:
  - MMQ rounds differently from the old path (yardstick above). The 40-prompt baselines stay identical (they
    take the unchanged path). `TITAN_PFS_KERNEL=gemv` is bit-identical but only ~420 tok/s.
  - Host experts are page-locked in place: about 8 GiB of the service's RAM becomes unswappable (there is no swap).
  - Short resumed passes and prompts under 128 tokens keep the CPU twin.
  - The 80B gains nothing at its current fraction.
- Keep 512-token chunks: 1024 is slower at 13k and OOMs at 28k; 2048 is worse.
