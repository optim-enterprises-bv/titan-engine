# kbench 2026-09-28: our cuda-oxide matmul kernels vs current llama.cpp on the service shapes

**Short answer: no.**
- **Dense Q8_0 at the service batches** (b1 and the b3 MTP verify) runs at llama.cpp speed: 0.85–1.1x.
- **Dense prefill MMQ** matches llama.cpp within 0–13% and is bit-identical.
- **The MoE experts lag.** They are the largest matmul share of service GPU time:
  - decode b1: 1.2–2.0x slower
  - MTP verify (b3): 1.5–2.6x slower
  - prefill, because the tiered path runs one gemv per (token, expert) pair: 4–31x slower
- **A fix for prefill already exists.** Our own MMQ-MoE port (mistralrs-quant `mmq_gguf_*_moe`) runs 1.6–2.5x *faster* than llama.cpp's MMQ and is bit-identical to it. The tiered path just doesn't call it.

## Setup
- **llama.cpp**: `~/ai/llama.cpp` build `acecd56` (2026-09-12), the reference commit of our fmt_mmq / q1_0 / iq4_nl / mxfp4 gates. Upstream HEAD on 2026-09-28 was `c2a9e1606`, 295 commits later (clone kept at `ref/llama.cpp-new`, not built).
  - In that range, `mmvq.cu` has one change (SM70-only crossover), `mmq.cu/.cuh` has only `e9f824d` (`llama_prec_policy` plumbing), and `vecdotq.cuh`, `quantize.cu` and `mmid.cu` have none. On sm_120 the MXFP4/NVFP4 MMQ default stays native W4A4 (with no prec metadata, `ggml_cuda_mmq_get_prec_src1` returns Q4). W4A8 applies only when the GGUF marks a tensor W4A16 or `GGML_CUDA_MMQ_PREC=q8` is set.
  - So acecd56 **is** current llama.cpp for these kernels, and rebuilding was unnecessary. The "SASS is the spec" gates against acecd56 remain valid for HEAD's default path.
- **Strata** pins llama.cpp `3cf03257` (2026-09-20; `third_party/ggml/VERSION.txt`, `CMakeLists.txt:506`), between the two. It hand-transcribes mmvq/vecdotq/dequant and compiles upstream's MMQ instances directly.
- **Harness** `kbench.cpp`: one process and one CUDA context. The same device buffers (random quantized weights, activations, uniform-random top-k routing) feed both sides:
  - llama.cpp through ggml graphs (`ggml_mul_mat` / `ggml_mul_mat_id`, and the fused FFN graph `up, gate, swiglu_split, down`);
  - ours through the service's exact launch sequence:
    - experts: titan `quantize_q8_1` + `<type>_q8_1_moe_gemv[_w]`, identity slot map;
    - dense b1: `launch_mmvq_gguf_quantize_q8_1_f32` + `launch_mmvq_gguf_q8_0_f32_plain`;
    - dense b2–8: `mmvq_gguf_q8_0_f32_rows<b>`;
    - dense b>8: `launch_mmq_quantize_q8_1_D4` + `launch_mmq_gguf_q8_0`, via `libtitan_oxide_ffi.a`.
- **Timing**: nsys GPU kernel time, summed over all kernels of the op (activation quantize included), median of 50 runs (11 runs for our tiered path at b≥2048), after 3 warm-ups. A 256 MiB memset before each run evicts L2 (weights cold, as in decode). CUDA-event medians for our side are in `out/*.tsv`. The GPU was exclusive: titan-mistral stopped, nothing else on the card.
- **Scope**: µs are for the whole op: all experts of one layer (top-8 of 256 for the 35B, top-10 of 512 for the 80B), or one dense projection.

llama.cpp's fused expert FFN (`up+gate+swiglu+down`) takes 35.8 / 74.6 / 178 / 2939 µs at b1 / 3 / 8 / 512. Our three separate launches sum to 50.7 / 122.3 / 289 / 18 158 µs, i.e. 1.42x / 1.64x / 1.62x / 6.2x slower. Fusing gate and up saves llama.cpp only about 10% at b1 (35.8 vs 11.9+11.9+16.1). Most of the gap is the kernels themselves.

## Where the gap comes from
- **MoE decode b1** (ncu, cold L2; `out/ncu-*.txt`):
  - The arithmetic is identical: 100% bit-equal outputs for Q4_K/Q5_K/Q6_K/MXFP4/IQ4_NL.
  - llama.cpp's `mul_mat_vec_q<12,1>` uses grid (512 rows, 8 experts) x (32,4). It reaches 17.1 µs and 277 GB/s under ncu.
  - Our candle-derived `q4k_q8_1_moe_gemv` uses one 128-thread block per (row, task). It takes 23.1 µs at 204 GB/s, with DRAM throughput at 30% vs 41%.
  - Q6_K down is the worst case (`q6k_q8_1_moe_gemv` 2.0x): it lacks the warp-rows variant that Q4_K/Q5_K got for k=512.
- **MoE b2–8 (MTP verify)**: llama.cpp switches to `mul_mat_vec_q_moe<type, ncols>`, which reads each routed expert's rows once for every token that picked it. It came from upstream PR #20905 (2026-03-29) and was extended to spec-decode in #27621 (2026-08-31); we have no port of it. Ours relaunches the whole gemv per (token, expert) task, so the cost grows almost linearly with b: 15.5 → 28 → 39 → 89 µs, against llama.cpp's 11.9 → 17 → 23 → 55 µs.
  - The outputs are still bit-equal for Q4_K/Q5_K/MXFP4.
  - For Q6_K and IQ4_NL at b≥2, only 38–49% match. llama.cpp's moe kernel reduces those types in a different order than its b1 kernel. If `mul_mat_vec_q_moe` is ported, gate it against the moe kernel, not the b1 one.
- **MoE prefill**: the tiered path's gemv at b512 is 5.7 ms (ncu: 2 097 152 blocks, SM throughput 78%, DRAM 30%: it recomputes each expert row per token with dp4a, no tile reuse). llama.cpp's MMQ takes 0.84 ms. Our `mmq_gguf_q4_k_moe` (tile x32) takes 0.42 ms. llama.cpp picks J=128 tiles for 512 tokens (`ncols_opt = ne12` on NVIDIA; RDNA3/4 only use tokens-per-expert), which leaves occupancy at 16.7% with 251 regs/thread and about 16 columns per expert.
  - The tiered prefill output is not bit-equal to llama.cpp's MMQ (max rel 1e-2): it uses the mmvq q8_1 activation path, not MMQ's, as expected.
  - The MMQ-MoE alternative is 100% bit-equal to llama.cpp's MMQ at every prefill shape tested.
- **Dense Q8_0**:
  - b1–3: parity or better. qkv b1 is 0.85x, a bit faster than llama.cpp.
  - b8 (`rows8`, one launch that reads weights once but reduces each column like b1) is 1.6–3.0x slower. This matters only for MTP ≥ 7.
  - Outputs differ from llama.cpp at decode (26–72% bit-equal, max rel 2e-7). mistralrs-quant's mmvq is its own reduction, which is expected and not a regression.
  - Dense prefill MMQ is 100% bit-equal and within 0–13% of llama.cpp.
  - lm_head b1 (664 µs, about 815 GB/s) is at DRAM roofline on both sides.

1. **`mul_mat_vec_q_moe`** (llama.cpp `ggml/src/ggml-cuda/mmvq.cu`, `mul_mat_vec_q_moe` + `mul_mat_vec_q_moe_launch`, from PR #20905/#27621), used for the tiered expert gemv at b1–8. It replaces `q4k/q5k/q6k(/mxfp4/iq4_nl)_q8_1_moe_gemv[_w]` for GPU-resident experts. It covers ranks 1, 2 and 4: about 12% of service GPU time. If decode were purely GPU-bound, that is up to about 13% more tok/s; the real gain is lower, since tiered misses run on the CPU.
   - Also port llama.cpp's b1 `mul_mat_vec_q<type,1>` MoE grid (row x expert). Its arithmetic is already ours (bit-equal), so the change is launch shape only: 1.2–1.3x at b1.
   - The slot-map indirection stays: `ids` → `slot_map[ids]`.
2. **Prefill experts through MMQ-MoE.** This needs no re-port: we already have a faster, bit-identical kernel (`launch_mmq_gguf_{q4_k,q5_k,q6_k}_moe`). Using it in the tiered path when all of a chunk's experts are resident, with misses still on the CPU twin, would cut the matmuls of a 512-token forward about 10x, from 777 ms to about 75 ms (experts 754 → 52 ms, plus 22 ms dense), below llama.cpp's 130 ms. This belongs to the prefill work in mr-pfs, not to this measurement. MXFP4 has no MoE MMQ in our tree; fmt_mmq's dense W4A4 kernels would need the mmid form (`mul_mat_q<MXFP4,...>` with `ids`/`expert_bounds`, llama.cpp `mmq.cuh` + `mmid.cu`).
3. **Fused gate/up + GLU** (llama.cpp `mmvq.cu` fusion args `ggml_cuda_mm_fusion_args_device`, `ggml-cuda.cu` `ggml_cuda_should_fuse_mul_mat_vec_q`): 1 launch instead of 2 plus a GLU kernel. About 10% on the expert FFN at b1, on top of (1).
4. **Dense Q8_0 `rows8`**: 1.6–3x at b8, zero weight today (MTP=2 → b3 is at parity). Revisit only if MTP ≥ 7.
5. **Nothing to gain** on dense Q8_0 b1/b3, lm_head, or dense MMQ prefill: they are within noise of llama.cpp or faster.
