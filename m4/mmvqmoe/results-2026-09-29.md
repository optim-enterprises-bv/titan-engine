# mmvq-moe: llama.cpp's batched MoE decode kernel in cuda-oxide, on the tiered expert path (2026-09-29)

**Result:** MTP=2 decode goes from 108.3 / 108.6 tok/s to 111.1 tok/s (+2.5% client-side, +3.1% server-side). That is a
back-to-back A/B on one binary (`TITAN_MMVQ_MOE=0 / 1 / 0`). MTP off gains about 1%. Expert kernel time per MoE layer
drops 12% at b1 and 27% at b3.

Output is unchanged, bit for bit:
- 35B 40/40 vs q35-prof;
- MTP=2 40/40 vs h-off;
- both again with a forced 50% CPU split.

The CPU twin needed no change. The service kernels reduce every column exactly as the old b1 kernel did.

## 2. The port and its gate (a)

Crate `oxide-kernels/mmvq-moe/` has 34 kernels, all with one titan ABI:

```
(w, x, ids, slot_map, out, n, k, k_padded, topk, input_dim1)
```

- **MoE grid** (`*_moe_mmvq*`): llama.cpp `mul_mat_vec_q_moe<type, 2>`. Grid (ceil(n/2), topk), block (32, b). One
  warp per token, 2 rows per block, no shared memory. A non-resident expert's warp simply returns.
- **b1 grid** (`*_moe_b1[_sk]*`): llama.cpp `mul_mat_vec_q<type, 1, small_k>` MUL_MAT_ID. Grid (ceil(n/rpb), tasks),
  block (32, 4), with rpb = 4 when small_k.
- **Formats**: Q4_K, Q5_K, Q6_K, Q1_0, IQ4_NL, MXFP4, NVFP4. The per-iteration float programs are titan-kernels-oxide's
  gated helpers, rewritten with `ld.global.nc` pointer loads. They were checked against the MoE instances' SASS: same
  FFMA/FMUL/FADD structure per format.
- **Reference**: `oxide-kernels/iq4_nl/ref/mmvq.cubin`. Its 64 MoE and K-quant b1 instances are SASS-identical to
  `~/ai/llama.cpp/build/bin/libggml-cuda.so` at acecd56 (checked with sass_cmp.py).

Gate (`target/release/mmvq_moe`, log `logs/kgate.log`): **PASS, 6048 comparisons, 208 MB of output compared, 0 differing
words.**

| part | what it compares | comparisons |
|---|---|---:|
| A | `*_moe_mmvq_llama` vs llama.cpp `mul_mat_vec_q_moe`, 7 formats; b = 1..8; top-8/3/1/10; gate/up and down input layouts; real 35B Q4_K/Q5_K/Q6_K experts plus synthetic normal and adversarial (NaN/inf/subnormal scales) data; odd n; ragged k | 2000 |
| B | b1-grid kernels vs llama.cpp's b1 kernel, launched per token as ggml does, small_k included | 288 |
| C | service kernels vs the deployed `*_q8_1_moe_gemv[_w]`, 30% of experts NOT_RESIDENT, sentinel-filled output, every byte | 3760 |

A and B together are 2288 comparisons against llama.cpp itself. The oxide side always reads a permuted slot buffer
through the slot map.

Sensitivity (D): llama.cpp's MoE float program does differ from the b1 program. Examples of differing outputs:
- Q6_K k=512: 776 053 / 1 724 416;
- IQ4_NL k=2048: 185 617 / 414 208;
- Q1_0 and MXFP4 at multi-iteration k.

Q4_K and Q5_K at the 35B shapes do not differ. This is the Q6_K / IQ4_NL mismatch kbench saw, and it shows the gate
detects reduction order.

Registers: `q4k_moe_mmvq` 64, `q5k_moe_mmvq` 64, `q6k_moe_mmvq` 61, `*_moe_b1` 40, no local memory.

## 3. CPU-twin decision: neither (i) nor (ii)

**Why llama.cpp's MoE float program cannot be used here.** Its lane chains `tmp = fma(d, sumf, tmp)` across quant blocks.
The b1 kernel instead keeps 4 per-warp partials. Using llama.cpp's program would change Q6_K (and IQ4_NL, Q1_0, MXFP4,
NVFP4) rows at b ≥ 2. That breaks more than CPU-twin identity: the MTP=2 == MTP-off guarantee (h-off) requires each
verify row to reduce exactly like the decode step it verifies.

**What the service kernels do instead.** They run llama.cpp's MoE geometry, but each lane executes the 4 warps of the b1
block as 4 virtual warps. Each virtual warp has its own partial and covers the same quant blocks. The partials are added
in warp order, then the butterfly runs.

**Consequences:**
- Output is bit-identical to the old kernel for every format, every k, and every placement (gate C).
- The CPU twin is unchanged.
- Batches with misses stay on the new kernel. Nothing falls back.
- K-quants keep candle's non-ftz program. The other formats keep llama.cpp's b1 program.

**Cost.** Against llama.cpp's own MoE kernel, the service kernel is 1.10–1.2x slower on Q4_K gate/up and 1.25–1.54x on
the Q5_K/Q6_K downs. Part of that is the float program, as the llama-program instance timings show. Part is the rest of
the kernel.

## 6. Why +3%, not +12%

The expert GEMVs are 10–15% of decode GPU time. Making them 1.3–1.8x faster at b3 saves about a quarter of that, which is
roughly 3–4% of GPU time.

The decode window is also 47–60% idle (tiered CPU-miss syncs and host work). Wall-clock tok/s follows GPU savings only
partly, because the idle time does not shrink.

The remaining gap to llama.cpp is 1.2–1.5x on the kernel, and it is the price of the b1-exact reduction. llama.cpp's own
float program would only be usable if MTP-verify identity with the b1 decode were given up.
